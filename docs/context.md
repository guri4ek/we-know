# Контекст і походження вимог

## Джерела

- [Вихідна розмова «Порівняння аналогів сайту»](https://chatgpt.com/c/6aca8ea5-04a0-83eb-8d1d-f80b57db4601), прочитана через доступну вкладку 2026-10-11: початковий опис, аналоги, Jev, уточнення категоризації, вибір режиму, NLP, механізми гумору, швидкість і постіронія.
- [Share-посилання від Serhii](https://chatgpt.com/share/6acb479e-9110-83eb-8773-c0a199dd4297), надане після читання приватної сесії; прочитане 2026-10-11 через публічний HTTP без браузера. Знімок завершується обговоренням гумористичних frameworks, швидкості та постіронії; ці джерела потребують окремої перевірки першоджерел.
- Поточна сесія запуску проєкту 2026-10-11: Symfony, не SPA, vanilla JS POST fetch на головній, ймовірні SQLite локально / PostgreSQL у production, мінімальний bootstrap без повної реалізації, англійська мова, Git у власника.
- Подальші уточнення цієї сесії: користувач дозволив Git і субагентів, доручив окремому агенту commit/push та доопрацювання документації; визначив UUID PK/created_at, гумористичний механізм у eligibility, вилучення revision і правила development migrations. Публікація продукту не доручена.

Це змістовний перенос контексту, не дослівний експорт. Твердження минулого ChatGPT про аналоги, наукові роботи, ціни й швидкість не вважаються незалежно підтвердженими фактами.

## Продукт

Робоча публічна назва — **Instant Answer**, згаданий домен — `instant-answer.net`, локальна назва та репозиторій — **we-know**. Право на домен і фінальне брендування не перевірялися.

Слоган: **We don't think. We know.** Філософія користувача: «максимально якісна реалізація максимально безглуздого продукту».

Це постіронія над упевненістю AI: стриманий, серйозний інтерфейс видає коротку, безапеляційну, абсурдну відповідь. Початкова аналогія — Magic 8-Ball. Важливі швидкість та можливість ділитися конкретною парою питання/відповідь через URL. Показники `0 questions understood`, `100% confidence` — сатиричний текст, не технічна телеметрія.

## Механіка Contextual Absurdity

Jev визначає очікувану форму відповіді (`intent`) і, за потреби, тему (`topic`). PHP вибирає випадкову готову фразу з придатного пулу. Модель не бачить повну бібліотеку і не визначає найсмішнішу фразу.

Початковий proposal таксономії; у scoped етапі 1 зафіксовано [baseline v1](content/taxonomy-v1.md) із поясненням ambiguity rules. Незалежна людська перевірка labels ще попереду:

- Intent: `YES_NO`, `WHEN`, `WHY`, `HOW`, `WHO`, `WHAT`, `HOW_MANY`, `CHOICE`, `OTHER`.
- Topic: `TECH`, `WORK`, `MONEY`, `LOVE`, `HEALTH`, `LIFE`, `GENERAL`.
- `ANY` — редакторська придатність універсальної відповіді, а не відповідь класифікатора.

Варіант fallback: точний `intent + topic` → `intent + GENERAL` → `ANY + GENERAL`. Наприклад, до питання про час пасує абсурдна дата, а не випадковий об'єкт. Це і відрізняє contextual від chaos. Якщо класифікація недоступна, універсальний fallback — деградація сервісу, а не приховане включення Chaos.

Збережена відповідь за permalink не повинна повторно запускати random або Jev. Повторне нове питання може дати інший результат; відкриття вже створеного URL — ні.

## Тон і UX: пропозиції, які підтримують концепцію

Один запит і один результат, без історії чату, імітації друку чи штучної паузи. Серйозна типографіка, мінімум декоративного шуму. Результат можна оформити як остаточне рішення з номером. Open Graph preview має допомагати поширенню.

Вихідна сесія пропонувала підзаголовок `The world's first uncertainty-free answer engine.`, псевдобюрократичні статуси, «сертифікати» та абсурдний changelog. Це творчий матеріал, не перелік обов'язкових екранів. About/FAQ мають пояснювати сатиричне розважальне призначення. Технічна документація та реальні помилки залишаються правдивими.

## Гумор: підготовка контенту та майбутнє дослідження

Цей підрозділ зберігає початковий стан обговорення; результати окремої перевірки 2026-10-11 наведено в наступному дослідницькому підрозділі.

У сесії згадано GTVH (Raskin/Attardo), JAPE, Reverse-Engineering Satire та Benign Violation Theory. Це напрямки для перевірки першоджерел, а не готові Composer-бібліотеки або перевірена наукова база цього плану.

Робоча авторська евристика асистента: очікувана форма + порушення логіки + deadpan-подача. Вона не є математичною формулою якості гумору.

Кандидати для `ANSWER_ELIGIBILITY.humor_mechanism`: metaphor, hyperbole, oxymoron, paradox, false causality, false authority, reversal, bureaucratic absurdity. Не змішувати механізми з категоріями питань. Поле заповнюється під час підготовки чи генерації відповіді; поточний random його не використовує. Пропонується один механізм із контрольованого string-переліку на eligibility, без зміни unique `(answer_id, intent, topic)`. Кілька механізмів — майбутнє рішення, щоб не множити candidate rows і не спотворювати random.

Поле лишається для можливої статистики; лайки, голосування або оцінка власником можуть з'явитися пізніше, але відповідні таблиці/маршрути не плануються як уже прийнята реалізація. Почати з підготовлених фраз; контрольовані шаблони на кшталт `On {day}, after {authority} approves {event}.` досліджувати окремо.

## Окреме дослідження гумору — 2026-10-11

Походження: нове пряме доручення Serhii після підключення й push репозиторію; воно дозволило локальні дослідження та документацію we-know попри reviewer-only default. У цій сесії — без субагентів, браузера, змін бізнес-коду/БД, особистих конфігурацій, Claude files і без commit/push. Це окремий обсяг, а не продовження попередньої Git-доставки.

Повністю прочитано наданий оркестратором `/private/tmp/we-know-humor-source.md`: витяги видимих user/assistant final повідомлень 77, 96, 98, 116 із [публічного share](https://chatgpt.com/share/6acb479e-9110-83eb-8773-c0a199dd4297), отриманого оркестратором через HTTP 2026-10-11. Сирий transcript/HTML не переносився в репозиторій. Цей матеріал задає provenance задуму, не підтверджує сам себе як наукове джерело.

Результати: [доказове дослідження механізмів](research/humor-mechanisms.md) та [самодостатній guide для Codex](content/answer-generation-guide.md). Перевірено первинні PDF JAPE, Reverse-Engineering Satire (AAAI 2019), McGraw/Warren 2010 і авторський виклад GTVH. Для GTVH доступні бібліографічний запис 1991 року та abstract авторського розділу 2020 року; повні тексти через видавців недоступні. Посилання, обсяг доступу та межі перенесення висновків зафіксовані в дослідженні.

**Нові редакторські пропозиції, не архітектурні рішення:** п’ять основних codes `bureaucratic_absurdity`, `false_causality`, `reversal`, `metaphor`, `hyperbole`; допоміжний `false_authority`; `oxymoron`/`paradox` залишені в резерві. Коди зберігають написання попередніх кандидатів. Guide дає контрольовані slots лише для офлайн написання завершених фраз, workflow відсіву, rubric, draft JSON і smoke corpus для всіх дев’яти intents. Приклади написані для цієї задачі; людського evaluation їхньої смішності ще не було. Таксономія intent/topic лишається proposal.

Прийняті межі збережено: Jev класифікує, PHP вибирає uniform random із першого придатного пулу, механізм готується на `ANSWER_ELIGIBILITY` і selector його ігнорує. Один primary mechanism на рядок — поточна пропозиція; overlap не породжує дубльованих кандидатів. Draft-формат не є schema/import contract; UUID PK/created_at у всіх таблицях, відсутність revision і правила міграцій не змінювалися. Runtime templates, Chaos/NLP, likes/votes та owner-review analytics залишаються відкладеними.

Дослідницький висновок: питання треба перевіряти перехресно з усіма фразами пулу, бо конкретний reply може бути вдалим лише на одному питанні. Особливо відкриті межі WHAT/CHOICE, одиниці HOW_MANY і доречність тематичних fallback. Смішність, переносимість на невідомі питання та втома від повторів — гіпотези для evaluation. Майбутні likes потребуватимуть урахування exposure/selection bias й не дають підстав змінювати random зараз.

## Швидкість і Jev

Попередня сесія наводила 140 ms P50, ціни й конкретні версії моделі. Ці числа не переносяться як гарантії чи актуальний бюджет. Для проєкту потрібен власний вимір із production-регіону та перевірка тарифу перед використанням.

Цілі з попередньої пропозиції: backend без зовнішньої класифікації до 20 ms, POST P50 до 300 ms / P95 до 700 ms, permalink server response до 100 ms. Це гіпотези для вимірювання, не виконані SLA.

Перевірена 2026-10-11 [офіційна документація TypeSafe](https://docs.typesafe.ai/introduction/quickstart) описує HTTP API з ключем, `state`, `model` та кількома `questions` в одному виклику. Це обґрунтовує адаптер для intent/topic. Наявність акаунта, ключа, безкоштовного тарифу та якість для наших питань ще не перевірено. Зовнішні платні виклики під час старту не робилися.

## Scoped етап 1 — 2026-10-11

Нове пряме доручення дозволило implementation, Composer, локальні документи й tests для taxonomy/контенту та Jev spike, без Git/deployment/наступних етапів. Після offline перевірок Serhii налаштував проєктний JEV_API_KEY та явно дозволив максимум 54 development live calls; окремий test credential відхилив як зайвий для одного малого акаунта. Ключ перенесено з versioned `.env` до вже ігнорованого `.env.local`, без виведення/логування.

Реалізовано typed classification boundary, Symfony HttpClient/DI, strict normalizer, versioned corpus (54 development/27 holdout), CLI evaluation й deterministic offline tests. Live: спочатку 54 calls із 0.30/0.40 s — 41 success і 13 timeout; після нового дозволу на 54 calls із 0.60/0.80 s — 54 success, 0 failures. Усі валідні responses — від `jev-1.13.0`. Деталі й semantic mismatches — [звіт](evaluation/stage-1-results.md). Це уточнює попередній стан «live не було», але не є production SLA чи independently verified quality. Holdout не викликався; rubric після development результатів не змінювався.

Обидва документи окремої дослідницької сесії прочитано й збережено; нові [ілюстрації форми](content/stage-1-answer-examples.md) лежать окремо з hold status. БД/selector/import/VERDICT/POST/permalink не реалізовано; decision_context не затверджувався. Claude material й особисті configuration/backups не змінювалися.

Після двох live development серій Serhii прямо обрав 600/800 ms як поточні timeout/max_duration defaults. Початкові 300/400 ms та їхній report залишено для порівняння; рубрику/labels не змінювали.

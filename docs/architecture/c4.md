# C4: target MVP architecture

Status: **target MVP model**, updated 2026-10-15. Implemented locally: Symfony/Twig, active v2 classification (Jev adapter/DI, taxonomy, 100-question corpus, tests, evaluation CLI), catalog/import, selector, answer creation/persistence, POST and permalink SSR. The dark-theme form/fetch, sharing, About/FAQ, data disclosure and styled errors are also implemented and offline tested. Production topology remains a target; actual checks are in [verification](../verification.md).

The diagrams use C4 semantics in ordinary Mermaid: each block names its element type and arrows are labeled. We Know is the system boundary; TypeSafe is external. A C4 container means an executable application or store, not necessarily Docker. The [official C4 model](https://c4model.com/diagrams) does not require all four levels; add L4 when implemented domain code has complex relationships worth explaining.

## L1 — System Context

```mermaid
flowchart LR
    visitor["Visitor<br/>Person<br/>Asks questions and shares answers"]
    reader["Link recipient<br/>Person<br/>Reads an immutable verdict"]
    editor["Owner / editor<br/>Person<br/>Prepares the answer catalog"]
    system["We Know / Instant Answer<br/>Software System<br/>Contextual absurd answers and permalinks"]
    jev["TypeSafe / Jev<br/>External Software System<br/>Classifies intent and topic"]
    visitor -->|"Submits question, receives verdict · HTTPS"| system
    reader -->|"Opens shared URL · HTTPS"| system
    editor -->|"Imports reviewed content · CLI"| system
    system -->|"Question and allowed categories · HTTPS JSON"| jev
    jev -->|"Selected enums and diagnostic scores"| system
```

TypeSafe does not generate the final phrase. Reading a saved verdict does not depend on TypeSafe. The owner will manage the catalog through explicit atomic CLI import; the MVP has no web admin.

## L2 — Containers

```mermaid
flowchart LR
    visitor["Visitor / recipient<br/>Person"]
    editor["Editor<br/>Person"]
    jev["TypeSafe / Jev<br/>External System<br/>HTTP API"]
    subgraph system["We Know — software system boundary"]
        ui["Web UI in browser<br/>Container · HTML / vanilla JS<br/>SSR pages; form fetch, no SPA"]
        app["Symfony application<br/>Container · PHP 8.4+ / Symfony 7.4 / Twig<br/>HTTP and CLI; classification, selection, persistence"]
        db[("Relational DB<br/>Container · SQLite local / PostgreSQL production<br/>Catalog, eligibility, verdict snapshots")]
    end
    visitor -->|"Enters question / reads result"| ui
    ui -->|"GET / and /a/id · HTTPS HTML"| app
    ui -->|"POST /answer · HTTPS JSON"| app
    app -->|"Server-side classification call · HTTPS JSON"| jev
    app -->|"Catalog reads / verdict writes and reads · DBAL SQL"| db
    editor -->|"Catalog import · php bin/console"| app
```

The same Symfony application delivers the UI; there is no separate frontend deployment. The database is one logical role, not simultaneous SQLite/PostgreSQL replication. Locally it is a file; production uses PostgreSQL. Public assets are served by a web server, a deployment detail rather than a separate business system. Development is PHP 8.4 with planned 8.5; Composer now requires/resolves PHP 8.4; actual runtime checks use 8.4.10.

## L3 — Components in the Symfony application

```mermaid
flowchart TB
    browser["Web UI<br/>External to application container"]
    jev["TypeSafe / Jev<br/>External system"]
    db[("Relational DB<br/>External container")]
    subgraph app["Symfony application container"]
        http["AnswerController<br/>Component · Symfony Controller<br/>Input, origin, limits, HTTP contract"]
        pages["Page controllers + Twig<br/>Component · SSR<br/>Home, About, permalink HTML"]
        usecase["AnswerQuestion<br/>Component · Application service<br/>Coordinates classify, select, persist"]
        classifier["JevClassifier<br/>Component · HttpClient adapter<br/>Implements QuestionClassifier; validated enums / failure"]
        selector["AnswerSelector<br/>Component · PHP domain logic<br/>Fallback tiers, deduplication, random"]
        catalog["CatalogRepository<br/>Component · DBAL adapter<br/>Active phrases and eligibility"]
        verdicts["VerdictRepository<br/>Component · DBAL adapter<br/>Immutable snapshots and ID lookup"]
        importer["ImportCatalogCommand<br/>Component · Console<br/>Validation and atomic content update"]
    end
    browser -->|"POST JSON"| http
    browser -->|"GET HTML"| pages
    http -->|"Validated question"| usecase
    usecase -->|"classify(question)"| classifier
    classifier -->|"One request with two Choice questions for intent/topic · HTTPS"| jev
    usecase -->|"Classification or fallback status"| selector
    selector -->|"First nonempty pool"| catalog
    usecase -->|"Save snapshot; commit before HTTP 201"| verdicts
    pages -->|"Find saved verdict by ID"| verdicts
    importer -->|"Validated catalog"| catalog
    catalog -->|"SQL / parameterized queries"| db
    verdicts -->|"SQL / short transaction"| db
```

Selectors do not know Jev transport/JSON. The adapter does not know the joke library. HTTP controllers do not implement classification/random selection. All components belong to one process/code project, not network microservices.

The catalog stores `humor_mechanism` on eligibility, prepared during content authoring and ignored by the selector. The user accepted VerdictRepository persistence of text snapshots, nullable eligibility FK with ON DELETE SET NULL, and short `decision_context`: actual provider, requested/resolved model, labels or failure, actual selected pool/tier/count/algorithm/mechanism and fallback reason. SQLite persistence is tested; PostgreSQL server acceptance is outstanding; the [data model](data.md) records the accepted requirements.

## Dynamic — creation and repeated reading

```mermaid
sequenceDiagram
    actor User
    participant UI as Browser / vanilla JS
    participant HTTP as Symfony Controller
    participant App as AnswerQuestion
    participant Jev as Jev adapter / TypeSafe
    participant Select as Contextual selector
    participant DB as Relational DB
    User->>UI: Submit question
    UI->>HTTP: POST /answer JSON
    HTTP->>HTTP: Validate input, origin and rate limits
    HTTP->>App: Valid question
    App->>Jev: Classify intent and topic
    alt Valid response within total deadline
        Jev-->>App: Classification
    else Timeout / provider failure / invalid response
        Jev-->>App: Typed failure
        App->>App: Mark failure and force universal ANY / GENERAL pool
    end
    App->>Select: Select from permitted tiers or forced universal pool
    Select->>DB: Read eligible active answers
    DB-->>Select: Candidate pool
    Select-->>App: Selected text, eligibility and selection context
    App->>DB: Persist text snapshots and accepted decision context, commit
    DB-->>App: Durable public ID
    App-->>HTTP: Verdict
    HTTP-->>UI: 201 JSON + Location
    UI-->>User: Plain text result and share URL
    User->>HTTP: GET /a/publicId
    HTTP->>DB: Read snapshot
    DB-->>HTTP: Same question and answer
    HTTP-->>User: SSR HTML + Open Graph
```

Rejected input/origin/rate-limit checks terminate before App/Jev. An empty universal pool or persistence failure returns 503 with no permalink: alternative failure paths to the successful save shown here. A permalink remains readable during Jev outages if the database is available.
